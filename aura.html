END-TO-END EXPERIENCE

回答、反馈、后台任务，各自有清晰的完成边界。

  1. 01

    恢复本轮需要的会话

    以 RedIM 原始消息为事实来源，加载 Redis 会话投影。缓存失效时用会话级租约锁合并回源重建，由持有者校验决定谁能提交结果。

  2. 02

    按预算组织上下文

    近期原文保留细节，Episode / Rollup 承接较早历史。摘要通过 Lua CAS 校验版本，写入屏障阻止旧记忆回填，避免压缩结果覆盖新消息。

  3. 03

    按需回查，再完成回答

    主模型结合现有 Sidecar 判断是否需要历史信息；只读工具按预算返回当前会话的时间原文与事件卡，仅用于本轮续答，不写回持久工作状态。

  4. 04

    回复完成后，再抽取事件

    将结构化事件抽取移到回复之后异步执行，保留事件主体、发生时间、计划或取消状态及更正关系，让事件整理不阻塞首轮回答。

反馈信箱与公告：从用户提交到官方回复

负责 Go 后端、Thrift IDL / SDK、HTTP 接口映射、Vue 管理端及 iOS / Android 客户端，完成图文反馈、消息分页、官方回复、已读未读、运营公告与通知跳转。结合 Proxyman 抓包和服务日志定位接口契约、环境配置与跨端状态问题。

先把消息写对，再发通知

用 MySQL 事务、行锁和复合唯一键保障消息序号分配与重复提交幂等，以快照分页、已读水位维护列表和红点。消息提交与通知发送分开处理，通知失败不会回滚已提交消息。

日报双队列：隔离即时请求与预生成

参与即时请求、后台预生成双队列及独立 Worker 池研发。Lua 原子抢占、租约续期和令牌校验支持超时接管，拒绝失去任务归属的旧 Worker 续期或提交。

让中断恢复有据可依

日报链路结合 Checkpoint 与有限重试复用已完成阶段，减少任务中断后的重复生成。任务归属、完成状态与可恢复阶段由程序维护，不依赖旧 Worker 对当前状态的判断。

MEMORY & CONVERSATION QUALITY

记住发生过什么，也尊重用户此刻的表达。

A：时间标注与原话溯源

保留会话时间信息和原始表达，让模型区分“当时发生”“现在计划”和“后来更正”。追溯依据来自用户原话，避免把助手历史推断当成用户事实。

B：结构化事件账本

记录事件主体、发生时间、计划 / 取消状态与更正关系。抽取在回复后异步进行，历史事件通过只读工具按需查询，减少旧话题被反复注入后重新带回当前对话。

压缩服务于连续对话

近期原文、Episode 和 Rollup 按 Token 预算组织。取消压缩入口对事件账本的直接注入，时间原文与事件卡仅在本轮需要时加载，防止摘要把无关历史固化为持续影响回答的状态。

语气约束与事实归因一起调整

针对刻薄回复、动机臆测和重复说教，联合调整人格提示、系统语气边界与本轮回答约束；区分用户原话、工具事实和助手推断，落实最新纠正优先、用户拒绝后停止推进。复用主模型与 Sidecar，不新增独立语气分类或生成后改写调用。

回复速度与事件质量的取舍

回归与评审口径

既有时间记忆方案完成个人泳道自测，并协同专职 QA 开展硬压缩回归。语气问题采用两位评审问题集合的合并口径；v8 是已完成该轮评审的候选版本。缓存结果来自本地冷缓存模拟，用于验证并发控制和消息完整性。

这些数据对应上述离线样例、候选版本回放和本地并发测试，用于评估方案取舍；不能直接推算线上全量会话的成功率、时延或用户满意度。
